## Quiz1：彩色影像轉灰階影像

### 基礎 / 

讀取 `Data/q1.jpg`，將彩色影像轉換成灰階影像，並比較原始影像與灰階結果。

OpenCV 讀取彩色影像時使用 BGR 順序，因此顯示前先使用：

```python
img_rgb = cv2.cvtColor(img, cv2.COLOR_BGR2RGB)
```

灰階影像則使用 OpenCV 的 `cv2.cvtColor()`：

```python
gray_img = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)
```

### 進階 / NumPy 與 OpenCV 比較

在 `Code/grayscale_np.py` 中，使用 BT.601 加權公式自行實作灰階轉換：

$$
Y = 0.114B + 0.587G + 0.299R
$$

由於 OpenCV 讀取的影像順序是 BGR，因此程式會分別取出 B、G、R 三個通道，再進行加權、四捨五入，最後轉換為 `uint8`。

以 $N=100$ 次重複執行，計算兩種方法的平均執行時間。接著使用下列指標比較結果：

- 最大像素差值：兩張灰階影像中最大的絕對差異
- 平均絕對誤差(MAE)：所有像素絕對差值的平均
- 非零差異像素數量與比例

差異矩陣的計算會先轉為整數型態，避免 `uint8` 相減時發生溢位：

```python
diff = np.abs(gray_cv2.astype(int) - gray_numpy.astype(int))
```
OpenCV 是已經由 C/C++ 優化過的影像處理函式，因此通常執行速度較快；NumPy 版本則是把灰階轉換公式清楚地寫出來，較容易理解演算法本身。

而且兩種方法的 MAE 很小、最大像素差值也不大，代表 NumPy 實作與 OpenCV 的結果非常接近。即使有少量像素不同，也通常是因為兩邊在浮點數計算或四捨五入時的細微差異，不代表影像內容有明顯改變。也就是說，這個實驗可以看出：NumPy 版本有助於理解原理，而 OpenCV 版本則比較適合實際應用與大量處理。

## Quiz2：Histogram Equalization

### 基礎 /

讀取 `Data/q2.jpg` 的灰階影像，使用 Histogram Equalization 增強影像的對比，並比較處理前後的影像與灰階直方圖。

OpenCV 的實作為：

```python
equ_cv = cv2.equalizeHist(img)
```

### 進階 / NumPy 與 OpenCV 比較

`Code/histogram_np.py` 使用 NumPy 自行完成直方圖均衡化，流程如下：

1. 計算 0 到 255 灰階值的出現次數。
2. 計算累積分布函數（CDF）。
3. 將 CDF 正規化至 0 到 255。
4. 使用查找表將原始影像映射成均衡化結果。

同樣以 $N=100$ 次執行比較 OpenCV 與 NumPy 的平均時間，再透過影像、直方圖與差異矩陣比較兩種方法的結果。

直方圖均衡化的目的，是把原本集中在某一小段灰階範圍的像素，重新分配到較寬的範圍。因此處理後通常會看到影像明暗對比變得比較明顯，直方圖的分布也會比處理前分散。

OpenCV 和 NumPy 的結果若看起來幾乎一樣，而且最大像素差值與 MAE 很小，就表示自行實作的 CDF 映射流程是正確的。兩者仍可能出現少數像素差異，原因可能是累積分布正規化、遮罩零值或整數轉換時的取整數的方式有些差異。而在速度方面，OpenCV 通常較快；NumPy 版本雖然可能較慢，但能清楚呈現直方圖、CDF 與查找表之間的關係。

因此，本題結果與Q1類似：OpenCV 偏向效率，NumPy 偏向理解與驗證。

## Quiz3：梯形校正與透視轉換

### 基礎 /

使用斜拍影像進行 Perspective Transformation，將影像校正為正視影像。目前 notebook 會處理：

```text
Data/q3-1.jpg
Data/q3-2.jpg
Data/q3-3.jpg
```

相關函式位於 `Code/perspective.py`，包括：

- `order_points()`：將四個角點整理為左上、右上、右下、左下
- `four_point_transform()`：根據四個角點計算透視轉換矩陣並進行校正
- `manual_select_points()`：開啟 OpenCV 視窗，讓使用者手動點選角點
- `auto_detect_quad()`：使用邊緣與輪廓自動尋找四邊形

### 手動點選流程

執行 Quiz3 的基礎 cell 後，每張影像會開啟一個 OpenCV 視窗。請依序點選：

1. 左上角
2. 右上角
3. 右下角
4. 左下角

### 進階 / 自動偵測

自動偵測流程會先將影像縮放至固定高度，再依序執行：

1. 灰階化
2. 高斯模糊
3. Canny 邊緣偵測
4. 膨脹與侵蝕，整理邊緣
5. 輪廓搜尋與四邊形近似
6. 四點透視校正

目前可調整的參數如下：

```python
MIN_AREA_RATIO = 0.1
CANNY_LOW = 60
CANNY_HIGH = 150
```

- `MIN_AREA_RATIO`：候選輪廓至少要佔影像面積的比例。提高可排除太小的雜訊，降低則有機會找到較小的卡片。
- `CANNY_LOW` 與 `CANNY_HIGH`：Canny 邊緣偵測的低、高閾值。邊緣不明顯時可降低閾值；背景雜訊太多時可提高閾值。

程式會在原圖上以紅線標示自動偵測到的四個角點，並顯示校正結果。`contour_4pt` 代表找到實際四邊形輪廓；若顯示 `minAreaRect_fallback`，表示未找到合適的四邊形，改用最小外接旋轉矩形近似，結果可能不如手動點選準確。

#### 不同拍攝角度的實驗方式

為了觀察演算法在什麼情況下開始失效，可以準備相同卡片在不同角度下的影像，或將現有影像依照拍攝角度分成低、中、高三組。每張影像都使用相同的參數執行自動偵測，再記錄以下結果：

| 觀察項目 | 判斷方式 |
| --- | --- |
| 是否找到四邊形 | `debug["method"]` 是否為 `contour_4pt` |
| 角點是否合理 | 紅線是否貼著卡片四個實際角落，而不是背景或外框 |
| 校正結果是否正常 | 卡片是否被拉回正視形狀，文字是否沒有嚴重拉伸或破碎 |
| 是否需要 fallback | 是否出現 `minAreaRect_fallback` |

可以用下列方式描述實驗結果：拍攝角度較小時，卡片的四條邊通常清楚可見，輪廓容易被近似成四邊形，因此校正結果穩定。當角度逐漸變大，卡片在影像中的投影會變得越來越扁，短邊可能只剩下很少的像素，邊緣也更容易被陰影或反光中斷。此時即使程式仍找到四個點，也可能是近似點，校正後會出現比例不自然、局部拉伸或方向錯誤。

本次程式沒有直接取得相機的真實拍攝角度，因此不應武斷地宣稱某個固定的幾何角度一定失敗。較合理的判定方式，是把「第一次出現角點明顯偏離卡片、校正結果不自然，或必須使用 fallback」的那一組影像，定義為目前資料下的失效條件。這個失效角度會受到影像解析度、卡片大小、背景、光線和鏡頭畸變影響。

#### 可能的誤差來源

- 卡片邊緣有圓角、陰影或反光，輪廓近似後角點可能偏移
- 背景中的其他強邊緣可能被誤認為目標輪廓
- 卡片與影像邊界太接近時，輪廓可能被截斷。
- 拍攝角度過大時，短邊可能太窄，Canny 邊緣偵測無法形成完整輪廓，且當卡片部分被遮擋時，輪廓不再是封閉的四邊形。
- 卡片有圓角時，`approxPolyDP` 會用直線近似圓角，角點可能落在真正角落的內側或外側。
- 透視變形太嚴重時，最小外接旋轉矩形只能提供粗略外框，無法完整描述真正的梯形。

因此，手動點選適合用來取得較精確的基礎結果；自動偵測則適合展示多張影像的自動化處理能力，並透過紅色角點檢查偵測是否合理。


透視校正本身不一定會因為角度變大而立刻失效；真正的關鍵是影像中是否仍保留清楚、連續且可辨識的四條卡片邊界。當卡片仍完整可見、背景沒有更強的干擾邊緣時，即使有明顯傾斜，透視轉換通常仍能正常工作。反之，當角度過大造成短邊消失、陰影遮住邊界、卡片被截斷，或背景輪廓比卡片更明顯時，失敗原因主要會出現在「角點偵測」，而不是透視矩陣計算本身。

## Quiz4：影像拼接

### 基礎：SIFT 特徵偵測與匹配

本題使用 `Data/q4-1.jpg` 與 `Data/q4-2.jpg`。兩張影像都拍攝同一個房間，且包含牆面與掛畫等重疊內容，因此可以利用共同特徵進行拼接。

程式流程如下：

1. 使用 SIFT 找出兩張影像的局部特徵。
2. 使用 BFMatcher 比較兩張影像的特徵描述子。
3. 使用 Lowe ratio test 排除不可靠的匹配。
4. 使用 RANSAC 估計 Homography，排除錯誤匹配。
5. 將第二張影像投影到第一張影像的座標系統。
6. 將重疊區域取平均，降低拼接接縫的突兀程度。

本次執行結果如下：

```text
左圖特徵點：2676
右圖特徵點：858
通過 ratio test 的匹配數：139
RANSAC 內點數：128
內點比例：92.09%
```

內點比例約為 92%，表示大部分匹配點都符合相同的幾何轉換，因此兩張影像可以成功拼接。結果會輸出至：

```text
Data/output/q4-stitched.jpg
```

拼接結果周圍可能出現黑色區域，這是因為透視轉換後的全景畫布比原始影像大，而畫布中有些位置沒有任何影像像素。這些黑色區域不代表拼接失敗。

### 進階：不同條件下的拼接效果

程式測試以下條件：

- 原始影像
- 右圖亮度增加 60
- 右圖亮度降低 60
- 右圖旋轉 8 度
- 右圖旋轉 20 度
- 將右圖裁切以減少重疊範圍
- 使用 CLAHE 增強局部對比後再進行特徵匹配

成功條件設定為至少有 12 個有效匹配，且 RANSAC 內點比例至少為 25%。實際結果如下：

| 測試條件 | 有效匹配 | 內點數 | 內點比例 | 結果 |
| --- | ---: | ---: | ---: | --- |
| 原始影像 | 139 | 128 | 92.09% | 成功 |
| 亮度增加 60 | 141 | 128 | 90.78% | 成功 |
| 亮度降低 60 | 5 | 0 | 0.00% | 失敗 |
| 旋轉 8 度 | 163 | 146 | 89.57% | 成功 |
| 旋轉 20 度 | 143 | 125 | 87.41% | 成功 |
| 減少重疊範圍 | 137 | 128 | 93.43% | 成功 |
| CLAHE 前處理 | 138 | 117 | 84.78% | 成功 |

#### 結果解讀

亮度增加 60 沒有明顯破壞拼接，因為 SIFT 使用局部梯度與影像結構，不完全依賴單純的像素亮度。旋轉 8 度與 20 度也仍然成功，代表 SIFT 對旋轉具有一定的穩定性；只要兩張影像仍有足夠的共同區域，Homography 就能找到合理的幾何關係。

本次最明顯的失敗條件是亮度降低 60。影像變暗後，牆面、掛畫與窗戶附近的局部紋理變得不容易辨識，導致有效匹配從 139 個大幅下降到 5 個，少於估計 Homography 所需的可靠匹配數量。這表示失敗發生在特徵偵測與匹配階段，而不是拼接函式本身。

減少重疊範圍的測試仍然成功，原因是兩張照片原本共有的牆面與掛畫特徵仍然足夠。若繼續縮小重疊範圍，直到共同特徵太少，匹配數與內點比例就會下降，最後無法計算可靠的 Homography。

CLAHE 前處理在本次影像中仍成功，雖然內點比例由 92.09% 降至 84.78%。這表示 CLAHE 增加了暗部的局部對比，但也可能同時放大雜訊或產生額外特徵，因此前處理不一定會讓每個指標都變好，仍應以實際匹配品質和拼接結果判斷。

### 可能的失敗原因

- 兩張影像的重疊區域太小，共同特徵數量不足。
- 影像太暗、過曝或有強烈反光，導致局部特徵消失。
- 拍攝角度差異過大，單一 Homography 無法充分描述場景變化。
- 場景中有移動物體，造成同一位置在兩張影像中不一致。
- 影像內容過於平坦，例如只有沒有紋理的白牆，SIFT 難以找到穩定特徵。
- 錯誤匹配太多，使 RANSAC 找不到一致的幾何模型。

因此，改善拼接穩定性的方向包括增加重疊範圍、避免過暗或過曝、使用 CLAHE 等局部對比前處理，以及調整 ratio test 與 RANSAC 閾值。判斷拼接是否成功時，不應只看程式是否產生輸出，也要同時檢查匹配數、RANSAC 內點比例與拼接接縫是否合理。
